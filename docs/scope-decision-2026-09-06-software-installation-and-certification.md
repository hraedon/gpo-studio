# Scope decisions, 2026-09-06 — Software Installation, and which evidence vocabulary is real

Status: **decided.** These are the two remaining `(c)` items from
[`plans-025-032-oracle-survey.md`](plans-025-032-oracle-survey.md) §8.2 and §8.3
that were waiting on a person rather than on Windows. The survey's own ruling
governs how they were taken: *"The five (c) items should be scheduled as
decisions, not as lanes, and should not sit in the same queue as the
measurements."* Neither of these consumed estate time.

The third `(c)` item, `hosting.py`, was ruled **harden** on 2026-08-07 and is
recorded in [`plan-032-shape-assessment-2026-08-07.md`](plan-032-shape-assessment-2026-08-07.md).
`publisher.py`'s review closed as WI-050, WI-051 and WI-052. With these two,
the `(c)` set is complete.

## Decision 1 — Software Installation is **read-only / preserve-only**. Do not generate `.aas`, and do not book the feasibility capture yet.

**The question** (§8.3): should GPO Studio write Software Installation at all?

**The ruling.** No. `software_install.py` stays where it is; the family's
capability ceiling is **preserve-only** — the state the 1.0 contract already
defines and already applies to unknown CSE content. Studio may in future *read* a
native backup's Software Installation content for review and diff. It commits to
generating nothing.

### Why, in the order the reasons actually carry weight

**1. The demand side is now measured, and it is zero.** This is the new input
the survey did not have. R6's census covers the extension lists of **26
production GPOs** in a live domain. The Software Installation CSE
`{C6DC5466-785A-11D2-84D0-00C04FB169F7}` appears in **none of them**. R8's
SYSVOL listings for three of those GPOs contain `Registry.pol`, `GptTmpl.inf`,
`ScheduledTasks.xml`, `Groups.xml` and comment sidecars — and no `Applications/`
tree at all.

**The honest weight of that: it is one estate, 26 GPOs, and a three-GPO SYSVOL
sample.** It is not evidence that the industry has abandoned Software
Installation, and this document does not claim it. It is evidence about the
estate this project can actually see, and it is enough to move a *priority*,
which is what a scheduling decision needs. If a second estate later shows heavy
use, that is a reason to revisit — the ruling is reversible and cheap to
reverse, because nothing is being deleted.

**2. The cost side is the most expensive unrun capture in the survey.** §3.7
names the conditions plainly: an MSI must exist inside an estate with **no
egress** (pushed over `psdirect` post-checkpoint-restore against a pinned
SHA-256), installing software on LabCL01 is **destructive**, and it needs a
checkpoint-restore path **no lane has ever exercised**. That is a first-of-kind
estate capability spent on a family with no measured demand.

**3. Even a favourable feasibility result would not make writing tractable.**
The `.aas` advertisement script is generated by the Windows Installer APIs from
the package. There is no documented format for Studio to emit, and this project's
entire evidence discipline rests on comparing against a native producer — which
here would mean reverse-engineering a binary format with no oracle for
correctness beyond "the endpoint installed something." The survey's hypothesis
that the AD-side `packageRegistration` objects are not carried by
`Backup-GPO`/`Import-GPO` remains untested, and under preserve-only it does not
need to be.

**4. What `software_install.py` currently is.** 487 lines with no serializer, no
parser and no file emitter, modelling a **workspace** lifecycle
(`pending|deployed|upgrading|removing|removed|failed|orphaned`) that no Windows
tool emits. Under this ruling most of it has no purpose. Per
[`domain-layer-status.md`](domain-layer-status.md) this is **not a deletion
order** — but it is explicitly a *stop-counting* order: the module must not
appear in any roadmap or status summary as progress toward a capability, because
the capability has now been ruled out of scope.

### What this ruling does not decide

It does not rule on **reading**. Parsing a native backup's Software Installation
content into a review surface is a smaller, well-shaped question with a cheap
oracle (a `Backup-GPO` of a GPMC-authored deployment, which is the §3.7
discriminator minus the endpoint leg). If a reader is ever wanted, that capture
is worth booking on its own merits. It is not booked now.

### Closing condition

Recorded in the capability matrix as `out of scope` for writing, with this
document cited. If the ruling is revisited, the trigger is a second estate
showing the CSE in use — not a re-reading of these same 26 GPOs.

## Decision 2 — `oracle_evidence.py` is the parity framework. `certification.py` is **superseded**.

**The question** (§8.2): two evidence vocabularies exist side by side and
disagree on `inconclusive`/`unsupported`, on boundary ownership, and on whether a
round trip counts as certifying evidence. Which one is real?

**The ruling.** `oracle_evidence.py`, the
`windows-oracle-manifest-v1.schema.json` contract and `boundary-matrix.md` are
the parity framework. `certification.py` is marked **superseded**: no new
consumer may be added, and removal is the default disposition when Plan 031 is
next opened, unless that plan identifies a need `oracle_evidence.py` demonstrably
cannot meet.

### Why this is not a close call

Three facts, each checked against the code rather than taken from the survey:

**1. It has no consumers.** `certification.py`'s only importer anywhere in
`src/`, `scripts/` or `tests/` is `tests/test_certification.py`. Meanwhile every
finalizer that has ever produced a live verdict —
`finalize_oracle_run.py`, `finalize_rsop_run.py`, `finalize_rsop_user_run.py`,
`finalize_endpoint_run.py`, `finalize_wp1b_run.py`, `finalize_wp2_import_run.py`
— goes through `oracle_evidence.py`. Fifteen live verdicts are bound to that
path. Zero to this one.

**2. It cannot express the states the boundary matrix requires.**
`EvidenceState` in `oracle_evidence.py` is
`Literal["pass", "fail", "unsupported", "inconclusive"]`.
`ConformanceResult` in `certification.py` is `passed: bool` plus
`skipped: bool` — the strings `inconclusive` and `boundary_owner` do not occur
in the file at all — and `evaluate_certification` counts a skipped case as
not-passed. That collapses *"we could not measure this"* into *"this failed"*,
which is exactly the conflation WP-6B's three-outcome rule was written to
forbid, and it destroys the distinction the boundary matrix calls load-bearing:
`unsupported` is an explicit capability downgrade, not a waived failure.

**3. It admits the thing this project exists to reject.** `round_trip` appears
14 times in `certification.py`; `_case`'s default `oracle` parameter is the
literal string `"round_trip"`, carried by fourteen cases in the default suite
including required ones. Plan 033's opening argument is that Studio's round-trip
tests prove only that Studio can read its own output. A certification framework
whose *default* oracle is a round trip would issue exactly the verdict this
project spent a year learning not to trust.

### The part that matters more than the ruling

A superseded module sitting in `src/` is harmless. A superseded module that
someone later wires into a real lane is not — and point 3 is precisely why that
would be worse than leaving it alone. So the ruling is enforced rather than
announced: `test_certification_module_has_no_production_consumer` fails if
anything outside `tests/` imports it.

That test is the whole safety property. If `certification.py` is eventually
deleted, the test goes with it; until then it is what makes "superseded" mean
something.

### What this does not claim

It does not say the *types* are worthless. `ParityEvidence` and
`EvidencePortfolio` are a reasonable sketch, and Plan 031's question — what a
portfolio of evidence across capabilities should look like — is real and
unanswered. What is settled is that the answer is built on
`oracle_evidence.py`'s four states and the boundary matrix's ownership rules,
not on a parallel two-state vocabulary that accepts round trips.

### Closing condition

Both recorded: the survey's §8.2 and §8.3 entries point here, and Plan 031's
scope is Plan 034's to restate. WI-056 tracks the removal decision itself, so
that "superseded" does not become another status that is true in one paragraph
and nowhere a person would look.
