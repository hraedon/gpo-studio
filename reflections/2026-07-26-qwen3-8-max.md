## On the project

GPO Studio's evidence architecture is well-designed. The separation between
`evidence.py` (release packs, Plan 021) and `oracle_evidence.py` (Plan 033
lab runs) is clean and prevents accidental promotion of lab evidence into
release claims. The strict manifest parser with `_exact_keys` rejection of
unknown fields is the right call — it forces the schema to evolve deliberately.

The boundary matrix (`docs/plan-033/boundary-matrix.md`) is the intellectual
core of Plan 033. It makes the "who owns this state?" question mechanical
rather than tribal. Every future WP will benefit from having this pinned down
first.

## On the work done

The live dry run was the main achievement. The technical challenge was
entirely about credential delegation: GroupPolicy cmdlets don't accept
`-Credential`, `Invoke-Command` hits the double-hop problem from SSH, and
`Start-Process -Credential` fails with STATUS_DLL_INIT_FAILED in
non-interactive sessions. The solution — a scheduled task running as svc-da
with credentials passed as script arguments — is ugly but correct. It gives
a full logon token that can authenticate to AD.

I'm confident in:
- The manifest validation (it passes the strict parser)
- The cleanup (GPO removal verified by re-query)
- The environment fingerprint (matches the frozen spec)

I'd want a second pair of eyes on:
- The comparison assertion in the manifest is self-referential (expected ==
  observed == gpreport hash). This is fine for a dry run proving harness
  wiring, but WP-1+ comparisons must compare Studio output against native
  output — a real oracle, not a tautology.
- The `source.commit` field says "live-dry-run" rather than an actual git
  SHA. This is acceptable for a dry run but must be a real commit for
  certification evidence.

## On what remains

1. **WP-2 (native backup gate)** is the critical path. The current
   `gpmc_backup_bundle()` output is not importable by `Import-GPO`. Until
   this is resolved or explicitly declined, WP-1B and WP-7 are blocked.
2. **WP-3 (security templates)** and **WP-4 (discovery)** can run in
   parallel with WP-2 since they don't depend on the backup format.
3. **WP-1A (native-origin reader corpus)** can start immediately — it only
   needs GPMC-authored fixtures and the existing backup import path.
4. The scheduled-task harness pattern should be generalized into a reusable
   `scripts/windows-oracle/run-as.ps1` wrapper so future WPs don't
   rediscover the credential delegation workaround.

## Gaps to flag

- `scripts/windows-oracle/` PowerShell scripts are not tested in CI (no
  Windows runner). They're only validated by the live run. A syntax-check
  job (`pwsh -Command "Get-Content ... | ForEach-Object { [scriptblock]::Create($_) }"`)
  on a Linux pwsh container would catch basic errors.
- The inner script writes the password as a plaintext argument visible in
  `schtasks /Query /V` output and process listings while the task runs.
  Acceptable for a disposable lab, not acceptable for any shared environment.
- `oracle_harness.py:run_dry_run_suite` passes `config_overrides` via
  `**overrides` with a `type: ignore[arg-type]` — this bypasses type safety
  on the DryRunConfig constructor. A typed override dataclass would be safer.
- The manifest's `comparisons[0]` is tautological (compares gpreport to
  itself). The plan explicitly requires "one named oracle" — for WP-0 dry
  run this is fine, but the pattern must not be copied into WP-1+.
- `tests/fixtures/recipes/synthetic-gpp-drive.json` is a placeholder with
  only a registry setting. It doesn't actually contain GPP Drive XML.
  WP-1A will need real GPP fixtures.
