## On the project

The discipline here is real and it is unusual. Most codebases have a rule that
says "don't claim more than you know"; this one has *machinery* — the bound-source
cost table prices an edit in estate runs before you make it, the work-item
register's index is held to the register's own status lines by a test, and the
pinning test for WP-4 was written to fail the moment its own brief was acted on.
That last one is the sharpest idea in the repo. A document that describes code
usually rots silently; this project made the rot mechanical.

What it buys is visible in the two defects the WP-3 object-security surface found
last week. The lane measures the bytes on the wire and certifies them; the
surface walks the rest of the module and found two things the lane structurally
could not. That is a genuine argument for the plan's ordering, and it repeated
here in a smaller way — writing the reader against the capture is what surfaced
that the fixture's provenance had the wrong GUID, a thing four people had read
past because no code executed it.

The cost is also real and I think under-acknowledged. Three of the four open
items before this session were blocked on one estate run, that run is blocked on
one unexplained failure, and the failure had no work item at all — it lived as a
paragraph four other documents pointed back at. The register exists precisely to
stop that, and the thing it was built to catch walked straight past it, because
the item that would have been filed was about *the estate* rather than about the
code. That gap is worth naming: this project's mechanisms cover claims about
code very well and claims about the lab hardly at all.

## On the work done

I am confident in the reader. It is tested against bytes hash-bound to what GPMC
wrote rather than against a fixture we invented, the round trip is against those
bytes, and a mutation that makes the parser return nothing now fails twelve
tests. That last property is not one I had before the review — and that is the
part of this session I'd want remembered.

My first version of `format_fdeploy` returned `raw_text` when a reparse matched,
copying `security_template.py`. For that module the passthrough is a fallback;
here it made the round-trip test `t == t`. Both tests passed against a parser
mutated to return zero sections, and one of them had a docstring citing WI-064 to
claim it was a real check. I wrote the tautology *and* the sentence asserting it
wasn't one, in a repo whose charter document names this exact failure. Copying a
precedent is not the same as understanding why it holds, and I did not notice the
difference until another model ran the mutation.

Two of the other three findings were mine too: a `Flags` length bound I added for
honesty introduced a 500 (`int()` refuses >4300 digits and raises a bare
`ValueError`), and `is_marker` as "no sections" meant a file of prose came back as
the marker GPMC writes — validated clean, with a report line asserting Windows
wrote it. Three untrue statements about a native artifact, from the module whose
whole argument is that it doesn't state what it hasn't measured. All fixed and
pinned, but the pattern is that my errors clustered where I was *most* confident
about the honesty framing, not least.

What I'd want a second pair of eyes on: the twelve unmeasured `KNOWNFOLDERID`
names. Nothing depends on them being right — an unknown GUID reports null, and
the endpoint now carries a limitation saying only Documents is corroborated — but
they came from recollection, which this project's own standard does not count as
evidence. And the fdeploy size/count ceilings (1 MiB / 5,000 / 5,000) are
plausible rather than derived; the real file is 458 bytes.

## Gaps to flag

- **The lab is not reachable from `mvmcc03`.** `~/.config/acb/capabilities.toml`
  registers only `e2e:chromium`; neither `cred:lab-hyperv-control` nor
  `cred:lab-guest-bootstrap` is provisioned, and `~/.claude/evidence-lab.env`
  does not exist. Credential capabilities are per-host by design. "The lab is
  available" does not imply this host can drive it — check `acb doctor` before
  planning estate work.
- **No log from the DNS failure is committed.** Three attempts are said to be at
  `C:\temp\lab\wi062-batch\attempt-archive\` on the controller; the repository
  holds one paragraph and nothing else. If that controller is ever rebuilt, the
  only record of a four-times-reproduced failure goes with it.
- **`docs/plan-033/wi062-batch.md:26-56` states a mechanism it did not measure.**
  "Every dynamic DC-locator record is deleted" — established through a resolver,
  as far as anything committed shows. The account may well be right. The step
  between symptom and mechanism was never taken and is one read.
- **The R3 provenance is corrected here and wrong upstream.** The
  `windows-console-driver` envelope (`docs/estate-window-3/records/r3-window3-record.json`)
  still calls `{FDD39AD0-…}` the Folder Redirection CSE GUID. The copy in this
  repo now carries a dated correction; the original does not, which is the wrong
  way round for a provenance chain. WI-067 stays open for that reason.
- **`fdeploy.py`'s ceilings are invented.** 1 MiB, 5,000 sections, 5,000 entries
  per section, added to `docs/import-resource-limits.md` as though measured. They
  are not; the only native file is 458 bytes. Same class of thing as
  `security_template.py`'s 4 MiB, which that document does not list at all.
- **Twelve of thirteen folder names are unmeasured** (`fdeploy.py`
  `KNOWN_FOLDER_NAMES`). Documented Windows constants, from recollection, with a
  limitation code saying so. Only Documents is corroborated by a capture here.
- **`missing_full_path` is severity `error`** on a shape no lane has measured
  (`fdeploy.py`, `validate_fdeploy`). I judged it structural rather than an
  opinion about acceptance, and kept it. A reviewer disagreed. It is a coin-flip
  I resolved by argument, not by evidence.
- **Nothing reads `fdeploy1.ini` on the import path.** An imported backup's
  reports and diffs are exactly as they were — the file is still a hash in the
  unmodeled-file inventory. The endpoint is the only route, which is unusual for
  this codebase and is WI-068.
